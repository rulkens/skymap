## Pre-execution rulings (user may overrule)

Each is settled for execution. An implementer who disagrees stops and reports;
they do not re-decide.

1. **Feel is a turntable** — yaw about the site's local vertical, pitch from the
   ground floor to overhead, zoom along the sightline, horizon level at all times.
2. **Band edges ship as 40 R / 80 R defaults with sliders** (§7.2). The eye-check
   settles a re-tune faster than analysis; the sliders make it a one-line data change.
3. **Drag signs ship as §4.6 derives** — `+Δx` raises the heading, `+Δy` raises
   the eye, so the grabbed side of the rover follows the cursor in both axes
   (§7.3). Confirmed at the eye-check (Task 10, item 2); an inverted verdict is
   two signs in one file plus one flipped test expectation. These are the body
   arm's **orbit** handle re-derived, **not** its tilt handle — do not "fix" them
   toward that sibling.
4. **Site up is the host radial** (§7.4), not the mesh body's own up. The bodies
   are analytic spheres; the alternative needs the `body-bounds-vs-surface`
   backlog item first.
5. **No new site is authored** (§7.5). Host-genericity is the deliverable and a
   **test fixture** on a non-Mars host carries it. `SURFACE_FIXED_SITES` keeps
   its four Mars rovers.
6. **The approach-owns-the-rung gate (§4.8) ships in THIS PR** (§7.1), never in
   prep — and only after Task 5's golden-trace pre-check has named what it moves.
7. **The site→body disengage lands the body arm anchored AT the site**
   (`anchorLocalM` = P, ruled §0). It is `toParent` and needs no code of its own;
   it is F4, and it lands inside Task 2.
8. **Tilt memory stays keyed by host/focus, not by frame.** Prep's `TiltMemory`
   (`{ hostId, rememberedTiltRad }`, keyed `hostOf(frame)?.id ?? focusBodyId`) is
   correct for the site rung by construction — a site's host is its planet, so a
   world → body → site descent **keeps** the remembered tilt. This plan must not
   re-key it to `frameKey`; doing so wipes the tilt on every disengage.

## Strategy

The mapped types are the compiler gate (§2.4): adding `'site'` to `RungKind`
without a complete `CAMERA_RUNGS.site` row cannot leave `tsc` green, and every
task here must leave it green. So the order is forced:

1. **Phase A (Tasks 1–4)** builds every piece of the site rung as a **pure
   function with no ladder consumer at all** — the pose type, the site point and
   its ENU, the floors, the two conversions, the band's tuning data, the
   turntable step. Nothing in the running engine changes; the suite is green for
   a boring reason, and every hard assertion in §6 is already pinned before the
   ladder sees the kind.
2. **Phase B (Tasks 5–6)** checks the golden traces for what F2 will move, then
   flips the kind and lands the row in one commit — a table row assembled from
   Phase A's helpers, which is why the atomic task is small.
3. **Phase C (Task 7)** changes the two chooser rules the rung needs to be
   reachable at all: the focus-subtree rule and the approach gate. This is the
   only task in the plan that changes incumbent behaviour outside a site frame,
   which is why its traces are pre-checked in Task 5.
4. **Phase D (Task 8)** is the surfaces — readouts, sliders, clip authoring.
5. **Phase E (Tasks 9–13)** is measurement, the user's feel gate, and the audits.

The two-frame descent test (world → `{body:'mars'}` → `{site:'curiosity'}`) lands
in **Task 7**, not Task 6: under today's focus rule the body rung will not admit a
rover focus, so that path does not exist until the subtree rule does.

## Global constraints

Binding on every task; do not restate them in commit messages.

- `npm run typecheck` and the task's named tests green **at the end of every
  task**, and a commit at the end of every task. A task that cannot leave the
  suite green is mis-sized — stop and report.
- **Golden traces.** `driverGoldenTrace`, `settleGoldenTrace` and `poseFold` come
  out byte-identical unless Task 5's pre-check named the step that legitimately
  moves. Any re-record carries a **parse-compared cell diff in the commit body**
  justifying every changed field. Unaccounted-for trace churn is a review failure.
- `noStoredRegimeFlag.test.ts` stays green with an **empty** allow-list. The tag
  is the regime; no boolean may shadow it.
- **Consumers never branch on the tag** except through the §2.6 grammar
  (`rungKindOf`, `frameKey`/`sameFrame`, `isWorldArm`, `hostOf`,
  `refoldTo`/`foldToWorld`, `stepRung`, `rowFor(...).step`/`.channels`). A new
  `=== 'absolute'` or `'site' in frame` anywhere is a review failure.
- **SI metres, f64, in the whole site path.** No `Mpc` enters it (spec 2 §10).
  Do **not** route the site ENU through `rotationSurfaceLocked` — that is the
  same derivation in world Mpc, for placing the body, and using it would put an
  Mpc↔metre conversion inside the camera path.
- **No renderer diff.** No slab, layer, shader, tile-planner or `.wesl` file is
  touched. A renderer file in a task's diff has taken a wrong turn.
- **Prep files are read, not rewritten.** Beyond the kind types, the new site row,
  the body row's focus rule (Task 7) and `stepRung`'s call site, nothing prep
  owns is edited.
- `type` aliases, never `interface`. One exported **type** per file in
  `src/@types/`, one exported **function** per file in `src/utils/`; filename =
  symbol name, deep relative imports, no barrels. Tests mirror the `src/` tree.
- Comments per [`conventions/comments.md`](../conventions/comments.md): module
  header ≤ 10 lines, comment lines ≤ half the code lines. Record units, frames,
  landmines and cross-file contracts; link the spec instead of summarising it.
- Tests per [`conventions/testing.md`](../conventions/testing.md). Specifically:
  **no** runtime tests of the new `.d.ts` shapes, **no** restatement of
  `DEFAULT_CAMERA_TUNING` or `SITE_RUNG`, **no mirror tests** — every expectation
  is a hand-computed value, a round trip, or an independent invariant.
- Any file move or rename goes through `npm run move-files -- <from> <to>`
  (`--dry` first), never `git mv` + hand-edited imports. No moves are expected in
  this plan.

### Task 1: the site pose, the site point, the site ENU, and the floors

**Files (create):** `src/@types/camera/SitePose.d.ts`,
`src/data/camera/siteRung.ts`, `src/utils/camera/sitePointBodyFixed.ts`,
`src/utils/camera/siteEyeFrame.ts`, `src/utils/camera/clampedSitePose.ts`
**Files (test):** `tests/utils/camera/sitePointBodyFixed.test.ts`,
`tests/utils/camera/siteEyeFrame.test.ts`,
`tests/utils/camera/clampedSitePose.test.ts`

**Consumes:** nothing from prep. `surfacePointBodyFixed`
(`src/utils/scene/surfacePointBodyFixed.ts`), `blendedEnuAt`,
`BODY_LOCAL_FRAME.pole`, `SurfaceFixedSite`, `MeshBody`, `EyeFrame`.

**Produces:**

```ts
// src/@types/camera/SitePose.d.ts — spec §4.1, field-for-field
export type SitePose = {
  readonly siteId: BodyId;
  /** Azimuth of the EYE as seen from the site, radians, north → east. */
  readonly headingRad: number;
  /** Elevation of the eye above the site's tangent plane, radians. */
  readonly elevationRad: number;
  /** Eye ← site distance, metres. */
  readonly rangeM: number;
};

// src/data/camera/siteRung.ts — spec §4.5; data, no sliders
export const SITE_RUNG: {
  readonly eyeFloorBoundingRadii: number; // 0.2
  readonly elevationCeilRad: number; // Math.PI / 2 - 1e-3
};

// src/utils/camera/sitePointBodyFixed.ts — host-fixed metres
export function sitePointBodyFixed(site: SurfaceFixedSite, hostRadiusM: number): Vec3;

// src/utils/camera/siteEyeFrame.ts — the ENU at P, as an EyeFrame
export function siteEyeFrame(pointBodyFixed: Readonly<Vec3>): EyeFrame;

// src/utils/camera/clampedSitePose.ts — §4.5's three floors, in order
export function clampedSitePose(pose: SitePose, body: MeshBody): SitePose;
```

**The change.** `sitePointBodyFixed` is
`surfacePointBodyFixed(site.latDeg, site.lonDeg, hostRadiusM + site.altitudeM)` —
deliberately the _same_ expression `deriveBodyStates.ts:82-85` uses to **place**
the rover, reading the same row and the same `SCENE_CELESTIAL_BODIES` ground
radius. That identity is the cross-file contract: if the camera's site point and
the body's placement diverge, the rover drifts in frame as the camera moves. Say
so in the header, in one line.

It takes the **row**, not an id, so the registry read happens once — in the row
cell (Task 6) — and a non-Mars host is a fixture literal rather than a mocked
module.

`siteEyeFrame` sets `localUp = normalize(P)` and takes `east`/`north` from
`blendedEnuAt(localUp, 1, BODY_LOCAL_FRAME.pole, null)` — at `blendW = 1` that
helper **is** the pure body ENU and its degenerate branch already covers a polar
site. `tiltRad` / `azimuthRad` are unread by `canonicalBasisAt`; set them to 0.

`clampedSitePose` applies, in this order: range floor
`body.standoffRadii × body.boundingRadiusM`; then the elevation floor
`asin(min(1, SITE_RUNG.eyeFloorBoundingRadii × body.boundingRadiusM / rangeM))`
**at the floored range**; then the elevation ceiling. The floor order is
load-bearing — the eye floor is range-dependent, so evaluating it before the
range floor leaves the eye under the ground.

**Tests (failing first):**

- `sitePointBodyFixed returns the hand-computed point for a fixture site` — a
  fixture row at a chosen lat/lon/alt on a 1000 m host lands at the vector worked
  out on paper, not re-derived with `surfacePointBodyFixed`.
- `the camera's site point is the point deriveBodyStates places the rover at` —
  for `curiosity`, the body-fixed offset agrees with `deriveBodyStates`'
  pre-rotation offset to under 1 mm. This is the cross-file contract; it fails if
  either side starts reading a bounding radius or drops `altitudeM`.
- `siteEyeFrame's east, north and up are orthonormal and right-handed` — at the
  equator and at a pole, so the degenerate branch is exercised.
- `clampedSitePose lifts a ground-grazing eye to the floor height` — elevation 0
  at 10 bounding radii comes back at the hand-computed `asin(0.02)`.
- `clampedSitePose floors the range and re-applies the elevation floor at the new
range` — a request inside the standoff comes back at the floor with the
  elevation the _floored_ range implies, not the requested one.
- `a straight-overhead request keeps the heading defined` — elevation π/2 comes
  back below the ceiling and the resulting basis is finite.

**Verify:** `npm test -- sitePointBodyFixed siteEyeFrame clampedSitePose`,
`npm run typecheck`.
**Commit:** `feat(camera): site pose, site point, site ENU and the rung floors`

### Task 2: the site ↔ body-arm conversions (this is F4)

**Files (create):** `src/utils/camera/sitePoseToBodyArm.ts`,
`src/utils/camera/sitePoseFromBodyArm.ts`
**Files (test):** `tests/utils/camera/sitePoseToBodyArm.test.ts`,
`tests/utils/camera/sitePoseFromBodyArm.test.ts`

**Consumes:** Task 1's four symbols; `canonicalBasisAt`, `bodyFixedEyeM`,
`BodyFixedPose` (`bodyId`, `anchorLocalM`, `eyeRelAnchorM`, `basisLocal`).

**Produces:**

```ts
// spec §4.3. `site.id === pose.siteId` is a precondition, not a runtime check.
export function sitePoseToBodyArm(
  pose: SitePose,
  site: SurfaceFixedSite,
  hostRadiusM: number,
): BodyFixedPose;

export function sitePoseFromBodyArm(
  arm: BodyFixedPose,
  site: SurfaceFixedSite,
  hostRadiusM: number,
  body: MeshBody,
): SitePose;
```

**The change.** `dir` is the unit site → eye vector,
`cos(elev)·(cos(head)·north + sin(head)·east) + sin(elev)·up`. Spec §4.3 gives
both directions in full; implement them as written.

**F4 lives here.** `sitePoseToBodyArm` sets `anchorLocalM = P` — the body arm is
anchored **at the site**, not at the body centre (ruled §0). That is also what
keeps `BodyFixedPose`'s stored magnitudes at rover scale instead of Mars-radius
scale. The disengage needs no code of its own: it **is** `toParent`.

`sitePoseFromBodyArm` **discards the incoming basis** — the site rung looks at
the site by construction, so entering re-aims onto `P`. That is intentional and
is what makes the round trip exact in one direction and a projection in the
other; both are pinned below. It ends with `clampedSitePose`.

**Tests (failing first):**

- `a site pose survives a round trip through the body arm` —
  `sitePoseFromBodyArm(sitePoseToBodyArm(s))` reproduces every field of `s` over
  the §6 fixture set: a polar site, the prime meridian, elevation at the floor
  and at the ceiling, range at the floor and at the release edge. State the
  tolerance in the test (1e-9 rad, 1e-6 relative on metres).
- `the body arm a site pose lands in is anchored at the site` — `anchorLocalM`
  equals the site point and `|eyeRelAnchorM|` equals `rangeM`. Without this the
  disengage silently re-anchors at the planet centre and the stored numbers go to
  Mars scale.
- `entering the site rung re-aims the camera at the site` — a body arm whose
  basis looks 90° away from the site comes back, through
  `sitePoseToBodyArm(sitePoseFromBodyArm(b))`, aimed **at** the site with the eye
  unmoved. A test asserting full symmetry here would pin the wrong contract.
- `a site on a non-Mars host round-trips identically` — the host-generic fixture
  (§7.5): a `SurfaceFixedSite` literal on a synthetic host, authored in the test
  only. Nothing about the conversions may be Mars-typed.

**Verify:** `npm test -- sitePoseToBodyArm sitePoseFromBodyArm`,
`npm run typecheck`.
**Commit:** `feat(camera): site ↔ body-arm conversions, anchored at the site`

readonly siteEngageR: number;

### Task 4: the turntable gesture register

**Files (create):** `src/utils/camera/steppedSitePose.ts`
**Files (test):** `tests/utils/camera/steppedSitePose.test.ts`

**Consumes:** Task 1's `clampedSitePose` and `siteEyeFrame`; `spentZoomFactor`
(clamped to [0.5, 2] per folded notch); `InputStep`; `canonicalBasisAt`.

**Produces:**

```ts
// spec §4.6. No memory parameter: a drag carries absolute pixels with
// `startPx` = the previous frame's end pixel, so MemOf['site'] is null.
export function steppedSitePose(
  pose: SitePose,
  input: InputStep,
  body: MeshBody,
  viewportPx: Readonly<Vec2>,
  fovYRad: number,
): SitePose;
```

**The change.** One drag mode, the turntable — no pan/strafe/look/tilt latch, so
none of `SurfaceGesture`'s machinery applies. The rate is the angle the pixel
delta subtends at the lens, the same law as the body arm
(`draggedSurfacePose.ts:46-50`): a drag of one screen height is one FOV of turn at
every range, and **no tuning constant exists to be wrong**. Spec §4.6 gives both
increments; the signs are ruling 3 above. Heading wraps; elevation and range go
through `clampedSitePose`.

Zoom is `rangeM *= spentZoomFactor(factor)` then the floors, re-evaluated at the
new range. **No cursor anchoring** — the turntable's pivot is the site, by
definition.

Every other input kind returns its input pose **by reference**, the discipline
`draggedSurfacePose.ts:131-133` records: an arithmetic identity is not an
identity for the full-pose byte bar.

**Tests (failing first):**

- `a drag of one screen height turns the turntable by one FOV` — hand-computed,
  asserted at two different ranges so the range-independence is pinned too.
- `the horizon stays level through an arbitrary drag sequence` — after a scripted
  sequence of mixed drags, the basis `up` from
  `canonicalBasisAt(siteEyeFrame(P), heading + π, π/2 − elevation)` lies in the
  plane spanned by the site radial and the sightline. **This is the test that
  would have caught the incumbent's rolling horizon.**
- `the eye never drops below the ground floor` — over the same sequence plus
  zooms, `rangeM · sin(elevationRad) ≥ SITE_RUNG.eyeFloorBoundingRadii ×
boundingRadiusM` at every step.
- `drag signs: +Δx raises the heading and +Δy raises the eye` — the §4.6
  derivation, pinned. If the eye-check (Task 10 item 2) rules the feel inverted,
  this expectation flips with the two signs.
- `a zoom-in burst stops at the range floor` — a large inward factor folds
  through `spentZoomFactor`'s per-notch clamp and lands at
  `standoffRadii × boundingRadiusM`, not inside the rover.
- `a non-drag, non-zoom input returns its pose by reference` — object identity,
  not deep equality.

**Verify:** `npm test -- steppedSitePose`, `npm run typecheck`.
**Commit:** `feat(camera): the site rung's turntable gesture register`

**Produces:**

```ts

/** True when `focusId` is `rungId` or reaches it by walking `bodyHostId`. */
export function focusInSubtree(focusId: BodyId | null, rungId: BodyId): boolean;
```

**The change, part 1 — the subtree rule.** Today the chooser releases whenever the
focused body differs from the engaged one and blocks engage the same way
(`regimeArmFor.ts:31-33,39`, re-homed by prep P3 into the body row's cells). It
becomes: **a focus whose `bodyHostId` chain passes through a rung's id keeps and
admits that rung.** `curiosity → mars → sun` passes through `mars`, so the Mars
arm holds under a rover focus. The walk needs a visited-set cycle guard — the
chain is seed data, and a bad seed would otherwise hang the frame loop.

**The change, part 2 — the approach gate.** The subtree rule alone strands the
approach: `followActive` is gated on the world arm (`cameraDrivers.ts:81-83`), a
rover's framing distance is metres, so an approach would cross Mars's engage band
~1500 km out, the follow row would go inactive mid-flight, and the camera would
park there. So **an approach owns the rung while it runs**: the rung step is
skipped while a follow row is winning and its memory is not yet `saturated`
(`cameraDrivers.ts:166`).

**Where the gate lives — a plan decision.** §4.8 says "`stepRung` is inert", but
its own analogy is the fold's `intent.dragging` skip
(`projectFramePose.ts:112-114`). Put the gate **there, beside that skip**, not
inside `stepRung`: `RungCtx` carries no driver state and widening it to carry
follow memory would braid the driver table into every row's context for one
caller's benefit. `stepRung` stays a pure function of the ladder.

**Golden traces.** Per Task 5's finding: byte-identical if the list was empty;
otherwise re-recorded with a **parse-compared cell diff in the commit body**
naming each changed field and the step it belongs to.

**Tests (failing first):**

- `a focus in the rung's host subtree keeps the rung` — focus `curiosity`, frame
  `{ body: 'mars' }`, the rung holds. Today's chooser answers `'absolute'`; this
  is the premise correction in spec §0 turned into a test.
- `a focus outside the subtree releases` — focus `earth`, frame `{ body: 'mars' }`.
- `the subtree walk terminates on a cyclic driver chain` — a synthetic cycle
  answers false rather than hanging.
- `an unsaturated approach holds the rung` — with a follow row winning and
  `saturated: false`, the fold returns the current frame even where the band
  admits a descent.
- `a saturated approach descends exactly one rung` — one, not two.
- `focusing a rover from the world arm reaches the site rung in exactly two
at-rest frames` — `absolute → { body: 'mars' } → { site: 'curiosity' }`;
