# Skymap — renderer map & WebGPU landmines

Read this before touching `src/services/gpu/`, `engine`, shaders, or debugging anything about rendering.

## Renderer quick map

- **`galaxyPointRenderer.ts` + `shaders/points/*.wesl`**: instanced billboards. Vertex stride is 52 bytes / 13 slots (xyz, magnitude, colorIndex, axisRatio + sign-bit fallback flag, baked paCos/paSin, radiusMpc, vMaxWeight, schechterRatio, angularDensityWeight, baked absMag). Galaxy-static values (PA rotation, absolute magnitude) are baked at upload, not recomputed per vertex. Identity is composed on the GPU from a per-draw `SourceUniforms.sourceCode` + `@builtin(instance_index)`, NOT baked per-vertex.
- **`galaxyPickRenderer.ts`**: r32uint pick texture. The fragment writes `(sourceCode << 27) | (localIdx + PICK_SENTINEL_OFFSET)`; see `src/data/selectionEncoding.ts` for the encoding (5 bits source, 27 bits localIdx, code 31 reserved as the all-ones sentinel). Source codes are append-only (the rule lives in `sources.ts`'s docstring) — same hygiene as enum values that get persisted to .bin, applied to POI-only codes too. Read the texture with `copyTextureToBuffer` for hover/click.
- **`textureAtlas.ts` + `texturedDiskRenderer.ts` + `shaders/texturedDisks/*.wesl`**: 2048×2048 atlas of 128×128 slots for galaxy thumbnails. LRU eviction.
- **`engine/subsystems/bitmapStreamSubsystem.ts`**: the shared atlas + fetch infrastructure — LRU clock, priority-queued concurrency-limited bitmap fetcher, and the `bitmapReady`/`bitmapFailed` memoisation pair. Enqueue is idempotent (don't re-add in-flight keys — see the module header for the bug history). Catalog- and atlas-agnostic; `engine/subsystems/galaxyAtlasSubsystem.ts` configures it with the galaxy thumbnail atlas's geometry and format. Thumbnail URLs are built by `src/utils/math/{sdss,dss}ThumbnailUrl.ts`: SDSS DR18 ImgCutout (CORS-safe) for SDSS galaxies; CDS hips2fits (CORS-safe DSS proxy) for 2MRS/GLADE.
- **`engine.ts`**: per-frame loop. Per-galaxy `apparentSizePx` gates thumbnail enqueue — but the inner loop hoists `Math.tan` and pre-computes `maxCamDistForVisibility` to avoid 2.5M trig calls per frame.
- **`renderScheduler.ts` + `engine.ts` frame tail**: render-on-demand. `requestRender()` from event handlers wakes the loop; the frame body re-schedules only while `autoRotate || currentTween || hasAnyAxis || queue.inFlightCount > 0 || recent-fade` is true.
- **Earth surface virtual texture** (`utils/scene/planEarthTiles.ts` + `engine/subsystems/earthTileSubsystem.ts` + `gpu/resources/textureAtlas.ts` + `data/bodies/earthTileParams.ts`): a page-table-and-atlas layer streamed on top of Earth's whole-globe albedo once the screen wants more detail than the base texture (8192×4096, pyramid level 4) delivers. `planEarthTiles.ts` is the pure per-frame quadtree plan — horizon reject, frustum reject, level-from-screen-density refine, window clip — its module header owns the algorithm; design rationale is in the plan and spec below, not restated here. `earthTileSubsystem.ts` turns a plan into atlas allocations and fetches and rebuilds the page table; `textureAtlas.ts` is the shared LRU slot atlas (also used by the galaxy thumbnail path) whose `allocate` returns `number | null`. The fragment lookup sits on the Earth pipeline (`gpu/renderers/bodies/earthRenderer.ts`, `gpu/shaders/bodies/earth/fragment.wesl`) at bindings 7 (`texture_2d<u32>` page table), 8 (`texture_2d<f32>` tile atlas) and 9 (a clamp-to-edge, no-mip-filter sampler distinct from the whole-globe sampler); both binding 7 and 8 carry 1×1 placeholders so the bind-group layout — fixed at pipeline creation — is valid before any tile has landed. Design record: [`docs/superpowers/specs/2026-07-28-earth-surface-virtual-texture.md`](superpowers/specs/2026-07-28-earth-surface-virtual-texture.md), [`docs/superpowers/plans/2026-07-29-earth-surface-virtual-texture-a-to-d.md`](superpowers/plans/2026-07-29-earth-surface-virtual-texture-a-to-d.md).
- **`volumeField/volumeFieldRenderer.ts` + `shaders/scalarVolume/*.wesl`**: additive 3D scalar-field raymarch (MCPM cosmic web, CF-4 flow) — one draw per active field, front-to-back over-compositing through a `texture_3d<f32>` cube. Each field carries two GPU-built mip pyramids, both filled at `upload()` time via the shared `gpu/lib/generateMipChain3d` primitive (never persisted, never CPU-computed): a display chain (box filter, self-referential) the raymarch samples through `textureSampleLevel` at a cone-footprint LOD, and a separate max-value pyramid — own base at dims/8, storing normalised **deviation** from the field's contrast center rather than raw voxel values, so the same skip logic is correct for both sequential (MCPM) and divergent (CF-4) palettes — the fragment shader's coarse-to-fine empty-space skip consults it against a cutoff derived live from the contrast/trim uniforms, so slider changes retune skipping with no rebuild. Cone-footprint LOD ties sample density to on-screen footprint via `pixelConeTan` (computed once per frame in `scalarVolumeLayer.ts`, already carrying the spec's factor of 2 — the shader multiplies it directly by march distance `t`, not `2*t`); `STEP_COUNT` is an iteration safety cap, not a density divisor — a per-iteration step floor guarantees the ray still reaches `tMax` within the cap at any LOD tier. Measured effect is pose-dependent (faster where the skip march finds empty space to jump over, a net tax where it doesn't — see the plan below for numbers); the `volume` render-target row stays at `scale: 3` (`renderTargets.ts`) after a 2026-08-19 regression at `scale: 2`. Design record: [`docs/superpowers/specs/2026-08-12-volume-raymarch-acceleration-design.md`](superpowers/specs/2026-08-12-volume-raymarch-acceleration-design.md), [`docs/superpowers/plans/2026-08-13-volume-raymarch-acceleration.md`](superpowers/plans/2026-08-13-volume-raymarch-acceleration.md).

## Things that have bitten us before

- **WebGPU `queue.writeBuffer` race**: interleaving `writeBuffer` with `submit` in the same frame doesn't preserve order — bake per-instance data into the vertex buffer instead of a uniform you mutate per draw.
- **Selection halo on wrong galaxy**: same root cause — selection index must come from a per-vertex attribute, not a uniform updated mid-frame.
- **CORS on DSS thumbnails**: ESO's DSS endpoint blocks browsers. Use CDS hips2fits (`https://alasky.cds.unistra.fr/hips-image-services/hips2fits`).
- **Retry storms on failed thumbnails**: the engine has BOTH a `bitmapReady` and `bitmapFailed` Set — the per-frame gate must check both. The image queue's `enqueue` is idempotent for in-flight keys.
- **`<details>` element collapsing on hover**: keep the InfoCard's outer wrapper element identical across renders so React doesn't remount and reset the `open` state.
- **iOS WebGPU is stricter than Chrome's Tint — a bad shader freezes the _whole_ canvas**: `texture_1d` sampling (`textureSampleLevel` has no 1D overload) is one example WebKit rejects but Chrome accepts. Because all HDR passes share one command encoder, an invalid pipeline makes `encoder.finish()` produce an invalid command buffer and `queue.submit()` silently drops the _entire_ frame — the loop ticks and the camera moves, but nothing ever presents. Symptom: navigation/toggles do nothing on iOS while the React UI updates fine, no thrown errors. Diagnosis: `createShaderModuleWithDevLog` (in `shaderCompileLogger.ts`) prints the real `getCompilationInfo()` error + offending line. Store 1D LUTs as N×1 `texture_2d`.
- **Earth's page table is rebuilt whole, never patched** (`earthTileSubsystem.ts`'s `uploadPageTable`): any residency change re-derives and `writeTexture`s the entire 128×128 `rgba8uint` table rather than touching only the cells an eviction or an arrival changed. It is a pure projection of the atlas's resident slot map (`buildEarthPageTable.ts`), so there is exactly one way for the table to be wrong — the projection — instead of one per mutation site. Patching incrementally would mean every eviction has to find and clear every cell that pointed at the freed slot.
- **`A = 0` in an Earth page-table cell means "sample the base texture"**: an all-zero table is the identity case, which is what makes the whole virtual-texture layer strictly additive — every failure path (no manifest, no atlas, a 404, ground beyond the window, the pre-engage 1×1 placeholder) collapses to it. `earthTileSubsystem.standDown()` writes an all-zero table on disengage rather than freeing anything.
- **`textureSampleLevel`, never `textureSample`, for the Earth tile atlas read** (`earth/fragment.wesl`): the atlas has a single mip level so there is no level to select, the call sidesteps WGSL's uniformity requirement for implicit derivatives, and those derivatives would be wrong anyway — the atlas uv jumps discontinuously at a slot boundary, so `dpdx` there reads garbage across the seam.
- **The Earth base level is a function of the session's TIER, not a constant** (`earthBaseLevelForTier.ts`): the three whole-globe surface textures are 2048/4096/8192 px, i.e. levels 2/3/4 on the ladder, so "the level the base already delivers" differs per tier and is derived from the tier the `earth:surface` slot actually committed (`earthSurfaceTier.ts` — the app-wide `state.tier` is only the request). A constant off the `large` ceiling made a default `medium` session stand down a level early and hand a z3 base to a z5 tile. The inversion uses an integer shift loop, never `Math.log2`: a fractional level makes every tile path a decimal and every `1 << (zWin - z)` span garbage.
- **The base level, the request floor and the bake floor are three different numbers**: the base level (above) is where `planEarthTiles` roots its quadtree walk and what the engage gate compares against; the request floor is `max(manifest levels.min, baseLevel + 1)`, derived per session in `derivePlannerParams`; the bake floor is `BAKE_MIN_LEVEL` in `tools/textures/buildEarthTiles.ts`, and the manifest is how the runtime hears about it. Rooting the walk at the request floor would make `zWin >= minTileLevel` true of every plan, leaving the engage gate (`plan.zWin > baseLevel`) unsatisfiable against its own floor; reading the bake floor as a runtime floor would make a shallower re-bake appear to do nothing.
- **`TextureAtlas.allocate` can return `null`**: when every slot was already claimed earlier in the same frame, it refuses rather than evicts (a consumer that wants more slots than the atlas has — Earth's tile planner asks for ~107 against 64 — would otherwise evict and refetch its own working set every frame). Every caller must treat `null` as "skip this request," not retry it.
- **`copyExternalImageToTexture`'s `flipY` differs between the whole-globe upload and the atlas upload, on purpose**: whole-globe body bitmaps (`earthRenderer.ts`, `texturedBodyRenderer.ts`, `cloudShellRenderer.ts`) upload with `flipY: true` so texture v=0 lands on the image's south row, matching the mesh's south-first v. `TextureAtlas.uploadBitmap` — shared by the galaxy thumbnail atlas and Earth's tile atlas — uploads with `flipY: false`, so within a slot v=0 is the source bitmap's own top row (for an Earth tile, its north edge). Neither call is wrong; they are two different textures with two different consumers, and the reconciliation between them lives on the CPU side, in the tile-index arithmetic (`earthTileXyForUv.ts`'s `1 - v` flip) and the fragment's matching `1 - in.uv.y`, not in either upload call.
