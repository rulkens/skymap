## Task quality verdict: **Changes requested** (one Critical, latent but real)

### Critical

**`downsampleLevel3d`'s fixed `srcZLow=2k`/`srcZHigh=2k+1` (and the mirrored X/Y clamp in `fs_max`) silently drops the trailing slice/row/column whenever the *parent* dimension is odd — breaking the max-reduction's conservativeness guarantee that Task 3's skip-empty-space raymarch will depend on.** `generateMipChain3d.ts:155-156` (Z) and `mipBlit3d.wesl:374-380` (X/Y, same pattern via `dims.x-1`/`dims.y-1` clamps).

Verified numerically against the exact cube dims this task's own test uses (178×300×182): depth axis level1→level2 is `91 → 45` (91 is odd — `floor(182/2)=91`). With `dstDepth=floor(91/2)=45`, the highest `srcZHigh` any destination slice ever reads is `min(2·44+1, 90) = 89` — **src z-index 90 (the last of 91 slices) is never read by any destination slice, in any of the 8 taps, at that level.** The clamp `min(2*dz+1, srcDepth-1)` is written to prevent an out-of-bounds read, but under `generateMipChain3d`'s own floor-sized loop (`dst.depth = floor(src.depth/2)`, always) the clamp condition can never actually fire — it exists syntactically but the boundary case it's meant to handle (`srcZLow === srcZHigh`, a legitimate trailing self-tap) never occurs, so the extra slice is simply dropped rather than folded in. Same drop reproduces on the width axis at the identical real dims: level1→level2 is `89 → 44`, and the max `xHigh` any destination column reads is 87, not 88.

This is exactly the case the brief called out for extra scrutiny ("Same scrutiny for fs_max's srcZLow/srcZHigh = 2k / 2k+1 with edge clamping for odd parent depths"). The report's own justification (`task-2-report.md`, "srcZLow/srcZHigh clamp" bullet) states the clamp "never triggers" under `generateMipChain3d`'s own chain and frames that as harmless, attributing the real trailing-tap need only to "Task 3's scratch-texture chain, where dst.depth may be `ceil(src.depth/2)`." That's true as far as it goes for filling remaining levels of a **display (`'box'`) texture** — floor-sized levels are mandatory there (real GPU mip dims are always `floor`), and `fs_box`'s continuous `boxZ = (dz+0.5)*ratio - 0.5` formula (verified algebraically and numerically: it reduces to the same normalized-UV mapping hardware uses for X/Y, so it naturally blends in the trailing slice with partial weight rather than dropping it — e.g. at the level-2 depth example above, slice 90 still gets ~0.49 weight in the last destination slice's trilinear tap). So **the box path is correct and this finding does not affect Task 2's currently-wired display chain.**

The risk is entirely in what Task 3 inherits: the brief's own design note states `generateMipChain3d`'s floor-sized loop is also the intended mechanism to fill "every level `generateMipChain3d` fills for a `'max'`-filter texture" (i.e., filling the *remaining* levels of the max-pyramid texture itself, after Task 3's initial cross-texture bootstrap populates level 0/1). Any such call — `generateMipChain3d(device, pyramidTexture, 'max')` — will hit this identical floor-sized coverage gap at every level with an odd parent dimension, silently under-reporting the true max wherever the dropped slice/row/column happened to hold the level's peak value. That is precisely the failure mode the plan amendment is meant to prevent ("correctness over the max-value pyramid depends on this being a true max"): a raymarch skip-empty-space gate built on a pyramid with this defect would occasionally skip over real density, producing a rendering bug with no failing test and no visible smoking gun (dropped-out structure, hard to attribute).

This doesn't block Task 2 on its own contract (box chain is correct, dead `fs_max` code isn't exercised by any current caller, `npm test`/`typecheck`/visual gate all pass as reported and independently reproduced). But it's a defect in the shared primitive Task 3 is explicitly designed to build on directly (`downsampleLevel3d`), and it's cheapest to fix now, before Task 3 threads more logic through it. Recommend surfacing to the plan author before Task 3 starts: either (a) `downsampleLevel3d`'s max-path needs a real third/self tap for a genuinely-dropped trailing index (which requires the *caller* to size `dst` via `ceil` rather than the shared `levelDim`/floor helper wherever a real coverage guarantee is needed — true for Task 3's cross-texture step, but not achievable for `generateMipChain3d`'s own further-level fill since GPU mip dims are floor-mandatory), or (b) the max pyramid's design needs to avoid ever calling `generateMipChain3d(..., 'max')` on its own texture past the first level and instead chain further levels via more `downsampleLevel3d` calls against `ceil`-sized scratch buffers, never touching floor-sized real mip levels for anything other than display.
